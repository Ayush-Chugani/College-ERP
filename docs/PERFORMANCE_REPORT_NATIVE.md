# Performance report: native PostgreSQL, before and after migration 051

This is the second measurement. The first ([PERFORMANCE_REPORT.md](PERFORMANCE_REPORT.md)) was taken on the embedded WASM database and found the row-by-row policy cost (KI-61); this one repeats it on a native PostgreSQL 16, applies the fix described below and measures again. Generated by `node tools/perf/report.mjs` from `tools/perf/last-run.json` (written by `tools/perf/run.ts`). Run date 2026-11-04.

## What was measured
- **Server**: PostgreSQL 16.15 (Ubuntu 16.15-0ubuntu0.24.04.1) on the development container (a shared, small machine: compare queries with each other, not with production latency).
- **Schema**: all migrations applied, row level security on, `ANALYZE` run after loading.
- **Data** (generated, not real): 20,003 students (each enrolled), 2,002 employees, 20,000 student activities, 165,027 audit rows, 50,000 sign-in rows, 15,000 payments, 5,000 fee accounts, 3,000 grievances. GEC Haveri is a single institution with a few thousand students, so this is roughly six times its size.
- **Method**: each query runs as the `authenticated` role with the JWT subject of a real fixture user (a registrar, a student, the super admin, a finance officer), so row level security is applied exactly as in production. Each query was run five times with `EXPLAIN (ANALYZE, BUFFERS)`; the table shows the median and the slowest run. "Big seq scan" marks a sequential scan over more than 5,000 rows.

## Findings and what was done
1. **Row level security was evaluated per row with a heavy lookup each time** (found by this run). `can_student()` and friends are called once per row by the policies; each call resolved the caller's identity and effective permissions through a multi-join view. A registrar's student list did not finish in 20 seconds at 20,000 students. Migration 051 (1) resolves the caller once per transaction and caches the decoded permission set in a transaction-local setting, (2) evaluates `covers()`, `can_student()` and `can_employee()` against that set in one function instead of several nested calls. The new functions are checked against the original definitions for every user, code set, target and mode in `tests/db/permission-equivalence.test.ts`. Result: the student list drops from more than 20 s to well under a second at 20,000 rows (about 30 microseconds per row), and in proportion at the real size.
2. **Review-queue notifications counted rows for people who cannot review anything.** `my_notification_count` took 642 ms for a student; it now skips queues the caller holds no grant for (4 ms).
3. **Activity lists scanned the big table once per status.** An optional status filter on the small lookup table made the generic plan loop over it; the filter is now resolved to an id once. `student_activity_list` went from 2.4 s to about 0.5 s.
4. **Missing indexes for time-ordered lists** (audit viewer, sign-in log, activity lists): added in 051.

## What is still slow, and why
- Anything that lists or counts `student` rows for a non-global user costs about 30 microseconds per row, because the policy decides row by row. That is 0.6 to 0.9 s at 20,000 students and about 0.1 s at the real scale. If the institution grows far beyond that, the fix is set-based policies (evaluate the caller's visible student ids once as an `IN (subquery)`) in the generated RLS, which is a larger change than this report justifies.
- `LIKE '%text%'` searches cannot use a normal index. Add `pg_trgm` indexes (`CREATE EXTENSION pg_trgm`) on `student(display_name)`, `student(student_number)` and `employee(display_name)` if searches become slow.
- The numbers above are single-user. Concurrent correctness is covered by `tests/concurrency`; a load test with many simultaneous users has not been run.
